# Integraciones realizadas — HU-04 FaceLit Backend

## ¿Qué se integró?

Se implementó el sistema de **inicio de sesión con gestión de roles, permisos y sesiones**.  
Involucra dos esquemas de base de datos: `roleandpermission` y `security`.

---

## ESQUEMA: `roleandpermission`

Todo lo relacionado con roles y permisos vive aquí.

---

### 📁 `auth/model/roleandpermission/`

#### `Role.java`
Mapea la tabla `roleandpermission.role`.  
Representa un rol del sistema. Usa el enum `RoleName` para evitar errores de tipeo.

```
id_role     → UUID, clave primaria
name_role   → Enum RoleName: ADMINISTRATOR | INSTRUCTOR | APPRENTICE
```

#### `Permission.java`
Mapea la tabla `roleandpermission.permission`.  
Cada permiso representa una acción específica dentro del sistema.

```
id_permission    → UUID, clave primaria
name_permission  → String: VIEW_OWN_PROFILE, ASSIGN_ROLES, etc.
description      → String opcional
```

#### `UserRole.java`
Mapea la tabla `roleandpermission.user_role`.  
Es la tabla intermedia que conecta un **usuario** con su **rol**.  
Un usuario solo puede tener un rol a la vez (restricción única en BD).

```
id_user_role    → UUID, clave primaria
user            → FK → security.user_app
role            → FK → roleandpermission.role
assignment_date → LocalDate, fecha en que se asignó el rol
assigned_at     → OffsetDateTime
```

#### `RolePermission.java`
Mapea la tabla `roleandpermission.role_permission`.  
Conecta un **rol** con sus **permisos**. Define exactamente qué puede hacer cada rol.

```
id_role_permission → UUID, clave primaria
role               → FK → roleandpermission.role
permission         → FK → roleandpermission.permission
assignment_date    → LocalDate
assigned_at        → OffsetDateTime
```

### 📁 `auth/dto/request/roleandpermission/`

#### `LoginRequestDTO.java`
JSON que manda el frontend al hacer login.

```json
{
  "email": "maria@gmail.com",
  "password": "Maria@123",
  "aceptoPoliticas": true
}
```

```
email           → @NotBlank @Email
password        → @NotBlank
aceptoPoliticas → @NotNull Boolean — debe ser true
```

---

### 📁 `auth/dto/response/roleandpermission/`

#### `LoginResponseDTO.java`
JSON que devuelve el backend tras un login exitoso.

```json
{
  "token": "eyJhbGci...",
  "role": "INSTRUCTOR",
  "permissions": ["VIEW_OWN_PROFILE", "VIEW_ATTENDANCE"],
  "userId": "uuid-del-usuario",
  "message": "Inicio de sesión exitoso"
}
```

```
token       → JWT generado — el frontend lo manda en cada request
role        → nombre del rol — el frontend redirige según este valor
permissions → lista de permisos del rol
userId      → UUID del usuario autenticado
message     → texto legible de confirmación
```

### 📁 `auth/exception/`

#### `LoginException.java`

```

```

### 📁 `auth/service/serviceImpl/roleandpermission/`

#### `LoginServiceImpl.java`
Implementa `LoginService`. Contiene toda la lógica del login en orden:

```
Paso 1  → Verifica aceptoPoliticas = true
Paso 2  → Busca Credential por email
Paso 3  → Obtiene User de la credencial
Paso 4  → Verifica AccountStatus = ACTIVE
Paso 5  → Compara password con BCrypt → incrementa failedAttempts si falla
Paso 6  → Resetea failedAttempts a 0
Paso 7  → Busca rol en user_role
Paso 8  → Obtiene nombre del rol como String
Paso 9  → Busca permisos del rol en role_permission
Paso 10 → Extrae nombres de permisos como List<String>
Paso 11 → Genera JWT con userId, email, role, permissions
Paso 12 → Registra sesión → userSessionService.registerSession(user) ← CAMBIO
Paso 13 → Devuelve LoginResponseDTO
```

> **Cambio realizado:** antes el `LoginServiceImpl` inyectaba `UserSessionRepository`
> directamente y creaba la sesión con 4 líneas de código.  
> Ahora delega esa responsabilidad a `UserSessionService` en una sola línea:
> ```java
> userSessionService.registerSession(user);
> ```

#### `JwtServiceImpl.java`
Implementa `JwtService` con la librería `jjwt 0.12.6`.  
Lee `jwt.secret` y `jwt.expiration` desde `application.yml` vía `@Value`.

```
generateToken() → construye el JWT y lo firma con el secret del .env
getClaims()     → parsea y valida el token, lanza excepción si es inválido
validateToken() → llama getClaims() en try-catch, retorna true o false
```

### 📁 `auth/controller/roleandpermission/`

#### `LoginController.java`
Endpoint público de login. No contiene lógica — solo recibe y delega.

```
POST /api/auth/login  →  público, no requiere token
```

---

### 📁 `config/`

#### `JwtFilter.java`
Intercepta **cada request** antes de que llegue al controller.  
Extiende `OncePerRequestFilter` — se ejecuta exactamente una vez por request.

```
Paso 1 → Lee header Authorization: Bearer eyJhbGci...
Paso 2 → Si no viene el header → deja pasar (endpoints públicos)
Paso 3 → Extrae el token quitando "Bearer "
Paso 4 → Valida token con jwtService.validateToken()
Paso 5 → Extrae role y permissions del token
Paso 6 → Construye authorities: ROLE_INSTRUCTOR, VIEW_ATTENDANCE...
Paso 7 → Crea UsernamePasswordAuthenticationToken
Paso 8 → Registra en SecurityContextHolder
Paso 9 → Continúa el request
```

#### `SecurityConfig.java`
Define las reglas globales de acceso por rol.

```
/api/auth/**        → público
/api/consent/**     → público
/api/catalogos/**   → público
/api/admin/**       → solo ADMINISTRATOR
/api/instructor/**  → ADMINISTRATOR e INSTRUCTOR
/api/apprentice/**  → todos los roles autenticados
```

## ESQUEMA: `security`

La sesión del usuario pertenece al esquema `security` junto con `user_app`, `credential`, etc.

---

### 📁 `auth/model/security/`

#### `UserSession.java`
Mapea la tabla `security.user_session`.  
Registra cada inicio de sesión exitoso del usuario.  
Un usuario puede tener **muchas sesiones** — una por cada login.

```
id_user_session → UUID, clave primaria
user            → FK → security.user_app (ManyToOne)
start_date      → OffsetDateTime, fecha y hora del login
end_date        → OffsetDateTime nullable — se llena al hacer logout
session_status  → Enum SessionStatus: ACTIVE | INACTIVE
```

---

### 📁 `auth/model/enums/`

#### `SessionStatus.java` ← enum
```java
ACTIVE    // sesión en curso
INACTIVE  // sesión cerrada (logout)
```

---

### 📁 `auth/repository/security/`

#### `UserSessionRepository.java`
Accede a la tabla `user_session`.  
No necesita métodos personalizados — `JpaRepository` ya tiene `save()`.

---

### 📁 `auth/service/security/`

#### `UserSessionService.java` ← interfaz
```java
UserSession registerSession(User user);  // se llama en cada login exitoso
void closeSession(UserSession session);  // se llamará cuando implementes logout
```

---

### 📁 `auth/service/serviceImpl/security/`

#### `UserSessionServiceImpl.java`
Implementa `UserSessionService`.

```
registerSession() → crea UserSession con startDate=ahora, status=ACTIVE → guarda en BD
closeSession()    → llena endDate=ahora, status=INACTIVE → guarda en BD (para logout futuro)
```

## Cambio clave en `RegisterServiceImpl`

Se agregó la asignación automática del rol **APPRENTICE** al momento del registro.  
Todo usuario nuevo empieza con este rol — el ADMINISTRATOR puede cambiarlo después.

```
Antes (paso 9): generaba el código de verificación directamente

Ahora (paso 9 nuevo):
→ busca el rol APPRENTICE en BD con roleRepository.findByNameRole(RoleName.APPRENTICE)
→ crea UserRole con user + role + fecha
→ guarda en user_role
→ continúa con el código de verificación (ahora paso 10)
```

>     (uuid_generate_v4(), 'INSTRUCTOR', NOW()),
>     (uuid_generate_v4(), 'APPRENTICE', NOW());
> ```

## Flujo completo del login

```
POST /api/auth/login { email, password, aceptoPoliticas: true }
        ↓
LoginController
        ↓
LoginServiceImpl
  1. valida políticas
  2. busca Credential por email
  3. verifica cuenta ACTIVE
  4. compara password BCrypt
  5. busca rol en user_role
  6. busca permisos del rol
  7. genera JWT
  8. registra sesión → UserSessionService.registerSession()
        ↓
LoginResponseDTO { token, role, permissions, userId }
        ↓
Cada request siguiente:
Authorization: Bearer token
        ↓
JwtFilter → valida token → carga contexto Spring Security
        ↓
SecurityConfig → verifica rol → permite ✅ o rechaza 403 ❌
```
